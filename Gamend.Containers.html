    Gamend.Containers (gamend_core v1.1.1361)

    Copy Markdown View Source

    Long-lived OCI containers, and the images they run, through the podman CLI.

    For a host that runs other programs beside itself on the machine it is on: a hosted Gamend per customer, a build sandbox. It is the CLI's verbs and nothing about what runs in them, so a host decides the limits, the mounts and the network, and this module only spells them as flags.

    Podman rather than Docker because it is rootless and has no root daemon to talk to. :runtime in a spec ("runsc", "kata-runtime") is how a host raises isolation without another driver: the same flags, a different OCI runtime.

    Errors

    Every call answers {:error, reason} on an expected failure:

    • :podman_not_found — no podman on the PATH.
    • :not_found — no such container, volume, network, image or build context.
    • {:podman_failed, verb, status, line} — the CLI exited non-zero; line is its last line of output, which is where podman puts the reason.

    A build answers its own, since its reason is a compiler's output, not podman's last line (build/2).

    Secrets

    Environment goes through a mode-0600 --env-file, never -e: arguments are world-readable in ps. The file is created empty at 0600 before the values are written, so they are never readable by another user, and it is removed as soon as podman create has read it.

    Users

    Rootless podman runs uid 0 of a container as the host user that runs podman, which owns every container, image and volume here, and any other uid as one of that user's subordinate uids. A container running someone else's code therefore runs as a numeric :user of its own, one per owner and never given to another while that owner's volumes exist, its volumes made for it (create_volume/3's owner:) or re-owned as they are mounted (:chown). A way out of it lands on a uid that owns that owner's files and nothing else.

    There is no --userns=auto. Rootless, each new mapping copies the image's layers chowned to it (6 s and 170 MB for a Gamend image, kept after the container is gone), a freed range goes to the next container while files written under it keep their owner, and an idmap volume is refused (podman 5.3).

    One container.

    :volumes sources are podman volume names or absolute host paths, mounted :rw, :ro or :chown: read-write once podman has chowned the source, recursively and on every start, to the user the container runs as. That is how a volume another user wrote passes to the container's own (a server's from before it had a uid); never on one another owner's container mounts too, which would belong to whichever started last. :tmpfs entries are "/path:options", as podman's --tmpfs takes them.

    :networks are the networks it joins (create_network/2), in place of podman's default. A container that must still reach the internet joins a network the host made beside an internal one, never "podman": the default has no DNS, so beside an internal network the container would resolve only that network's names (podman 5.3). :network_alias is a name the others on those networks reach it by, besides its own.

    :user runs it as that user instead of the image's own: a name, "uid" or "uid:gid". An image that starts as root to drop to its user (a database's entrypoint) runs under the floor's dropped capabilities only when it starts as that user. A name is looked up in the image's own /etc/passwd, which can map it to 0, so an image someone else built gets "uid:gid" (a uid alone that its passwd lacks runs in group 0). It is the host's to choose, never an owner's (see Users above).

    Functions

    build(context, opts)

    @spec build(Path.t(), keyword()) ::
  {:ok, %{id: String.t(), log: String.t()}} | {:error, term()}

    Build an image from the directory context with its Dockerfile, and name it tag:. Answers the image's id and the end of the build's output: {:ok, %{id: "sha256:…", log: "…"}}.

    opts:

    • tag: — the name, required.
    • dockerfile: — the file, relative to context and inside it (podman's own Containerfile, then Dockerfile, when not given). A file outside it, or a symlink, is refused with {:unsafe_dockerfile, path}: the CLI reads it from this machine, so it could be anything here.
    • target: — the stage to build; the last one when not given.
    • args: — %{"NAME" => "value"} for the Dockerfile's ARGs. Never a secret: they are in the image's history and on the command line.
    • labels: — set on the image.
    • memory_mb:, cpus: — what the build's RUN steps may use.
    • runtime: — the OCI runtime its RUN steps run under (runsc). A podman CLI talking to a remote service (CONTAINER_HOST) does not take one, and the build fails on it.
    • network: false — no network for RUN steps. On by default, since a build fetches its dependencies.
    • timeout_ms: — the build is stopped past it, SIGTERM then SIGKILL 10 s later, and answers {:build_timeout, log}. Through a remote service (podman 5.3), the build stopped there too, with no image and no working container left. No limit by default.
    • on_output: — a function given each piece of output as it comes, for a host showing the build live.

    No hardening floor, unlike create/1: a Dockerfile's RUN expects the root a build normally has (apt drops to its own user with setgroups, which a container without capabilities refuses). Rootless podman, and runtime: for someone else's Dockerfile, are what keep a build in.

    Errors besides the module's: {:build_failed, status, log}, the build's exit status and the end of its output, and {:build_timeout, log}.

    update(name, limits)

    @spec update(String.t(), keyword()) :: :ok | {:error, term()}

    Change a container's limits while it runs: cpus:, memory_mb: and pids:, all three required.

    A host gives a booting container more CPU than its size and takes it back once it answers, since a boot is the one time a small server is CPU-bound.

    All three because podman 5 writes the whole resource set on an update: a call with only --cpus left the container with no memory and no pids limit (memory.max read max afterwards, podman 5.3.1).

    write_env_file(path, env)

    @spec write_env_file(Path.t(), %{required(String.t()) => String.t()}) ::
  :ok | {:error, term()}

    Write env to path as a podman --env-file, readable by its owner only.

    The file is created empty at 0600 before the values go in, so they are never readable by another user, even for the moment between the two. A key or value holding a newline, a carriage return or a NUL is refused with {:unsafe_env, key}: the file is read a line at a time, so a newline in a value is a second KEY=value line the caller never set. The caller removes the file once podman has read it.
