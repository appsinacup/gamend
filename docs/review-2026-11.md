## Fix first

- [x] **CL-1 ✔ Create form passes admin-only fields through.** `gamend_cloud`
  `cloud_server_new_live.ex:123` → `Servers.create_server/2`: the non-admin
  branch (`servers.ex:368`) passes the raw attrs on, so `comped`, `trusted`,
  `custom_size`, `host_mounts`, `trusted_env` (`servers.ex:458,475`) and
  `import` (`servers.ex:388`) are taken from the client. A crafted LiveView
  event gives a free, trusted server with host mounts, or imports another
  owner's upload dir, which `node_worker.ex:144` then `File.rm_rf`s as root.
  Fix: whitelist create attrs (`slug`, `icon_url`, `size`, `database`,
  `group_id`, code fields, `code_token`); set `comped`/`trusted`/`import` only
  in `import_server/2` or the admin branch; refuse an import dir outside
  `Imports.config(:dir)`.
  **Done (2026-11-13):** `create_server/2` keeps only `@create_fields`; trust
  fields and `comped` only in the admin branch; the import dir is an argument
  only `import_server/2` passes, and the jobs refuse any other dir
  (`:not_an_import_dir`).
- [x] **GC-1 ✔ A notification's group is the client's.** `gamend`
  `Notifications.group_of/1` (`notifications.ex:375`) believes
  `metadata["group"]`; `send_notification/2` → `upsert_notification`
  (`:599`) stores the client's metadata. A friend sends `"group":"account"` and
  the server emails under a group that cannot be turned off, from the site's
  domain, past the recipient's opt-outs (`reports`, `payments` too). A non-string
  group (`1`) raises in `NotificationsLive.Sections.build` (`sections.ex:60`)
  and `NotificationEmail.group_label/1`, so the recipient's `/notifications`
  crashes on every mount. Fix: the group is server-owned — drop `group` and
  `email_now` from client metadata; `group_of` accepts only a binary that
  `Preferences.group/1` knows.
  **Done (2026-11-13):** `upsert_notification` drops `group` and `email_now`
  from the caller's metadata; only `notify/3` sets a group. `group_of/1` takes
  only a group `Preferences` knows, `Sections` stacks only by a binary type, and
  the email's label falls back to "Other".
- [x] **GC-2 ✔ A guest who signs in loses what they bought.**
  `accounts/guest_merge.ex:234` skips entitlements with `source_purchase_id`;
  `user_auth.ex:81` then `delete_user(guest)` cascades those rows, nils
  `purchases.user_id` and `DeletedAccountSubscriptions.cancel` kills the Stripe
  subscription. Guests can reach checkout. Fix: move the guest's purchases and
  their entitlements to the account in the merge (longer row wins on a key
  collision), before the delete.
  **Done (2026-11-13):** `Payments.move_purchases/2` (one durable transaction,
  both users' rows locked in id order) is a `GuestMerge` step before
  `:entitlements`. A guest row that lasts longer takes over the account's row.
  Known edge: if the account holds a longer granted row (a lifetime grant), the
  guest's moved Stripe subscription keeps charging with no row, the same as any
  granted account that also subscribes.
- [x] **FG-1 ✔ Gzip bomb on git push.** `forge` `git/plug.ex:303-347`: up to
  272 MB of body held in memory, then `:zlib.gunzip/1` with no output cap
  (`:339`). A 10 MB push of zeros inflates to ~10 GB and the node (web +
  builds) dies. Fix: stream `read_body` chunks to the file and inflate with
  `:zlib.inflateInit(31)` / `inflateChunk` under a byte cap.
  **Done (2026-11-13):** The body is spooled to disk; a gzipped one is inflated
  with `safeInflate`, with what arrives and what it inflates to capped at max
  push + 16 MB (413); a bad stream is 503.
- [x] **CL-12 ✔ The operator's mail credentials are in every tenant's
  environment.** `servers.ex:1431-1446` `mail_env/1` gives every container the
  relay username and password; `backups.ex:136-141` hands the shared S3 key to
  every container when Garage is off. Fix: per-server relay credentials with a
  rate limit (or a local relay that authenticates each server by its own token
  and pins From); refuse untrusted servers in the shared-S3 mode.
  **Done (2026-11-13):** Per-server Resend key (`servers/mail.ex`,
  `MAIL_API_KEY`, `MAIL_DOMAIN_ID`) kept in `Gamend.Secrets` and revoked on

  backups are for trusted servers only. Operator: set the keys, Apply settings
  everywhere, rotate the shared Resend password.

## Design notes (not bugs)

- **gamend_cloud lifecycle:** desired state plus one reconciler per server.
  Owners write intent (`on`, image, size, node, settings digest) with conditional
  writes; one process per server brings podman in line. Most transient statuses,
  the dedupe and the unsafe retries go away. A `generation` on the row fences
  moves; liveness runs apart from job slots; no sweep deletes data.
- **Matchmaking:** a new lobby seats party members one by one, a backfill uses
  `join_lobby_with_party`: two paths, different gates. Unify on one party-aware
  seat.
- **`Gamend.Names`:** ~80 small enum modules and two custom lints, but no CHECK
  constraints in the database. `Ecto.Enum` or one module per context would be
  leaner. Debatable; not planned.
- **Admin CSS:** `gamend.css` scans all of `gamend_web/lib`, admin included. An
  admin-only stylesheet would cut public CSS.

## Sound as designed

Quest codes (one use per player is the unique index, capacity a conditional
update); `Gamend.Rating` (Glicko-2 and Elo maths correct); friends, groups,
tournaments, ready checks and results follow the rule-at-the-write pattern;
forge's git token design (one project, one hour, read only, out of URLs and
logs); the server-authoritative voyage; bc901feac fixed the real cause
(reloader, repo check and SRI hash per request).
