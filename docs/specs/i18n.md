# i18n: one place for every translatable string

Design spec. Moves the two bodies of user-facing text that gettext does not
currently reach — the theme config and the titles/descriptions on quests,
leaderboards and tournaments — onto the same PO pipeline the rest of the UI
already uses.

Goal: a translator opens one CSV per locale and sees every string the server
can show, whether it came from a JSON file, a database row or a HEEx template.

## Where we are

Gettext is healthy and covers the UI: **30 locales**, nine domains
(`default`, `errors`, `notifications`, `auth`, `groups`, `leaderboards`,
`lobbies`, `settings`, `achievements`), and Romanian `default.po` is 229 of
231 translated. Locale resolution already works end to end —
`GameServerWeb.GettextSync` puts the locale on every backend, driven by
`Plugs.Locale`, `Plugs.LocalePath` and `OnMount.Locale`. There is a CSV
round-trip for translators (`mix gettext.export_csv` / `import_csv`) which
already knows how to walk the theme JSON.

Two things sit outside it.

### 1. Theme text lives in one JSON file per locale

`GameServer.Theme.JSONConfig` loads `<base>.<locale>.json` and never the base
path itself, so a locale is a **whole copy of the config**. Comparing
`modules/example_config.en.json` against `.ro.json` field by field:

| | Count |
| --- | --- |
| Values identical across locales — URLs, icons, styles, layout hints | 56 |
| Values that actually differ — the translation | 30 |

So roughly **two thirds of every locale file is duplicated structure**, copied
30 times. That is the whole cost of the current design, and it is already
being paid:

- **All 29 non-English files have drifted.** Every one is missing
  `theme_color.light` and `theme_color.dark`. Someone added a config field,
  updated English, and 29 files silently did not get it — so every
  non-English visitor falls back to the hardcoded `#ffffff` in
  `host_layouts/root.html.heex:89` instead of the configured dark
  `#1a1a2e`. That is not a translation bug. It is a **config** field lost
  because config and translations share a file.
- **gamend's own theme has no locale files at all.** `theme/` contains only
  `config.en.json`, so `gamend.appsinacup.com` serves English nav ("Play")
  to Romanian visitors while the gettext-backed chrome around it is
  translated. That is the visible symptom.

Crucially, **zero non-text values differ per locale** — no localised images,
no per-locale URLs. Nothing but text needs to vary, so nothing is lost by
moving text out.

### 2. Quest, leaderboard and tournament text is never translated

All three carry `title` and `description` columns and are rendered raw. They
are created two ways, and the difference decides the mechanism:

- **From code** — a plugin's `after_startup` (the eight sample quests in
  `example_hook`), seeds. String literals, present at extraction time.
- **From the admin UI** — `admin_live/{quests,leaderboards,tournaments}.ex`.
  Typed by a human at runtime.

A `.po` file is compiled from msgids that existed when extraction ran, so
**gettext cannot hold admin-created content** — there is no extraction step
between typing a title and rendering it. "Put them all in PO" works for the
first origin and is impossible for the second. The design has to say so
rather than pretend otherwise.

## Architecture

One rule for both bodies of text: **store the source string, translate at
render.**

### The trap this avoids

The obvious version is wrong:

```elixir
create_quest(title: gettext("Welcome aboard"))   # ✗
```

That translates once, at creation, in whatever locale the server booted in,
and freezes it into the database for every user. The pair gettext provides
for exactly this:

```elixir
# definition — registers the msgid for extraction, returns the string unchanged
create_quest(title: dgettext_noop("content", "Welcome aboard"))

# render — the viewer's locale, falling back to the source string
Gettext.dgettext(GameServerWeb.Gettext, "content", quest.title)
```

Verified against the live backend with the value held in a variable, exactly
as a database row would be:

```
stored value (as in a DB row): "Actions"
rendered via dgettext:         "Acțiuni"
unknown string falls back to:  "Admin typed this at 3pm"
```

That last line is what makes this shippable: admin-typed content costs
nothing and breaks nothing. It renders untranslated instead of blowing up, so
the render side can land for every entity before a single msgid exists.

### Two new domains

- **`theme`** — strings extracted from the theme JSON.
- **`content`** — titles and descriptions defined in code for quests,
  leaderboards and tournaments.

Separate domains keep a translator's CSV legible and let the theme extractor
own its `.pot` without fighting `mix gettext.extract`.

### Theme: one config, translated fields

`GameServer.Theme.JSONConfig` stops deriving locale paths and loads a single
`<base>.json`. Translatable leaves pass through
`Gettext.dgettext(backend, "theme", value)` on the way out.

Which leaves are translatable is **one list in one module**, shared by the
renderer and the extractor so the two cannot disagree:

```elixir
@translatable ~w(label title text tagline description alt site_message cta subtitle)
```

A key not on that list is config and is never touched — which is what keeps
`theme_color`, `icon`, `url` and the layout hints out of translator CSVs, and
what stops the drift described above from being possible at all.

`host_layouts.fetch_theme/1` currently asks the provider for a locale and
falls back `es_ES → es → default`. That logic **disappears**: gettext already
does locale fallback, so the layout just asks for the theme once.

Caching in `:persistent_term` stays, but keyed on nothing — there is one
config now. Translation happens per render, which is a map walk over ~36
strings and cheaper than the current per-locale file read.

### Content: noop at definition, dgettext at render

> **Revised during implementation.** `dgettext_noop` turned out to be
> unusable at the definition sites that matter: a plugin is its own Mix
> project and does not depend on `:gettext`, so the macro is not in scope
> (`Gettext.Macros is not loaded`). It would also have missed every
> admin-created row. `mix gamend.content.extract` reads the msgids from the
> **database** instead, which covers both, and matches how the theme is
> extracted — from the data, not from the code that produced it. The rest of
> this section stands; only the extraction step changed.

- Definition sites wrap literals in `dgettext_noop("content", …)`:
  `example_hook`, `demo.seed`, and polyglot's plugin.
- Render sites translate: `quests_live`, `leaderboards_live`, the tournaments
  pages, and the realtime payloads that carry a title.
- **Admin pages deliberately do not translate.** An admin editing a quest must
  see the string that is actually stored, or they will "fix" a translated
  title and overwrite the source.

No migration and no schema change: the columns already hold the source string.

## Migration

**Theme.** The existing exporter already flattens the config to paths
(`navigation.primary_links[0].label` = `"Joacă"`), so each locale file pairs
against English at the same path. For every locale, emit
`msgid <english> / msgstr <localised>` into `theme.po`, then delete the 29
files. `theme/config.en.json` becomes `theme/config.json`;
`modules/example_config.*.json` is deleted outright: nothing loaded it, so it
was a second theme free to drift from the real one.

**Content.** None. The render change is inert until msgids exist.

Per CONTRIBUTING this is a clean break: a host with
`config.<locale>.json` files finds them ignored. `[breaking]` in the
CHANGELOG, and the loader logs once if it sees a locale-suffixed file next to
the base, naming the migration task — that is a diagnostic, not a fallback.

## Update everywhere

- **`GameServer.Theme.JSONConfig`** — single config, translate on read; drop
  locale-path derivation. **`host_layouts`** — drop `try_primary_or_fallback/2`.
- **`mix gamend.theme.extract`** — walks the config into `theme.pot`, sharing
  the `@translatable` list. Wired into `precommit` beside the settings
  generators, `--check`ed in CI.
- **`mix gamend.theme.migrate_locales`** — one-shot, path-pairs the existing
  locale JSONs into `theme.po` and reports what it could not match.
- **`gettext.export_csv` / `import_csv`** — read and write the `theme` domain
  instead of locale JSON files.
- **Render sites** — `quests_live`, `leaderboards_live`, tournaments,
  `host_layouts`; admin pages left raw on purpose.
- **Definition sites** — `example_hook`, `demo.seed`, polyglot's plugin.
- **Stale domain** — `achievements.pot`/`.po` outlived the feature
  (CHANGELOG: "Achievements removed — replaced by permanent quests"). Delete
  across 30 locales.
- **Docs** — the theme guide (`priv/docs/10-setup/50-theme.md`) rewritten
  around one config plus PO; `translations/README.md` gains the theme domain;
  CHANGELOG `[breaking]` + `[added]`.

## Deferred / rejected

- **Translating admin-created content: deferred.** It needs a per-row store,
  not PO. The natural shape is a `translations` JSONB column
  (`%{"ro" => %{"title" => …}}`) — all three schemas already carry a
  `metadata` JSONB, so it is additive. Until someone asks, admin content
  renders in its source language, which `dgettext` already does for free.
- **Path-keyed locale overrides (`sections[2].title`): rejected.** It looks
  simpler than gettext and reads the same as the CSV export, but it breaks the
  moment a section is reordered — every translation silently shifts one slot.
  Keying on the source string survives reordering, which is the whole reason
  gettext works that way.
- **Translation keys in the database (`title_key: "quest.first_login.title"`):
  rejected.** It forces plugin authors to maintain a key *and* a PO entry, and
  leaves admin-created rows with no key at all. Passing the English string as
  the msgid costs one wrapper.
- **Machine-translating the 30 locales: out of scope of the *design*.** It was
  then done as a content pass through the CSV round-trip the design provides,
  and needs native review before it can be called correct.

      pages show the stored source string.
